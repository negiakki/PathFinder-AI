PathFinder AI — Pre-Implementation Analysis

Complete review of PRD · UI_SPEC · PROMPT_SPEC · ARCHITECTURE · TASKS · PROJECT_STATUS · BOB

1 · Project Understanding

PathFinder AI is a stateless, AI-powered career counseling web application targeting Indian school students in Classes 9–12, particularly from rural and underserved communities. The product is intentionally scoped as a focused MVP with no user accounts, no database, and no persistent history.

Core User Journey

Landing Page → Career Discovery Session (one question at a time) → AI Analysis Screen (animated) → Career Report (9 cards) → PDF Download

Technology Stack

Key Design Constraints

  • Exactly one AI request per assessment — no split calls.
  • AI must return strict JSON only — no Markdown, no explanations outside JSON.
  • Backend owns all resource URL mapping — AI never generates URLs.
  • All API keys kept server-side — never exposed to the browser.
  • No database, no auth, no chat history (MVP scope).
  • React Context for state — no Redux.

Assessment Branching

The question set diverges after the first two common questions (Class, Language). Classes 9–10 focus on stream selection; Classes 11–12 focus on degree programs, entrance exams, and career opportunities.

Career Report Structure (9 Cards)

  1. Career Snapshot
  2. Why This Recommendation
  3. Career Opportunities (grid)
  4. Academic Pathway (vertical timeline)
  5. Skills to Develop (chips)
  6. Personalized Learning Roadmap (timeline)
  7. Learning Resources (cards with links)
  8. Words of Encouragement
  9. Download Career Report (PDF)

2 · Conflicts, Ambiguities & Missing Information

CONFLICT C1 — PDF Generation Location

PRD: Lists "Download Career Report" as Card 9 and implies client-side download.

ARCHITECTURE: Defines a PDF Service inside the backend and lists pdf generation under backend Utility Layer.

Resolution (PRD wins): Use a client-side PDF library (jsPDF + html2canvas, or react-to-pdf) on the frontend. This avoids an extra round-trip, keeps the backend stateless, and eliminates the need for a backend PDF route. The backend PDF Service in ARCHITECTURE is a legacy mention that conflicts with the stateless design principle.

CONFLICT C2 — Phase Numbering Mismatch (TASKS vs PROJECT_STATUS)

TASKS.md lists Phases 1–12 where Phase 5 = Backend API & IBM Integration combined, Phase 6 = Career Report, Phase 7 = PDF Export.

PROJECT_STATUS.md lists Phases 1–12 where Phase 5 = Backend API, Phase 6 = IBM watsonx.ai Integration (separate), Phase 7 = Career Report, Phase 8 = PDF Export.

Resolution (TASKS takes precedence, ARCHITECTURE used to arbitrate): Keep IBM integration within Phase 5 since they are inseparable. Update PROJECT_STATUS phase list to match TASKS order after Phase 1.

AMBIGUITY A1 — "Preferred Language" Question Scope

PRD lists "Preferred Language" as a common question, and PRD also lists "Regional Language Support" as Out of Scope. The question seems to collect the student's preferred communication language for the AI, but since only English is supported in v1, the question's effect on the AI prompt is unclear.

Recommendation: Retain the question but always send English to the AI. The field can be used in a future version. The question UI can offer "English" and optionally "Hindi" (greyed out with "Coming Soon") to signal future roadmap.

AMBIGUITY A2 — Total Question Count & Progress Bar Denominator

PRD and TASKS define the question topics but do not specify the exact number of questions per path (9–10 vs 11–12). UI_SPEC shows "Question 3 of 10" as an example, suggesting ~10 questions, but this is illustrative only.

Recommendation: Define a concrete question bank in code during Phase 3. ~10 questions for each path is a reasonable target matching the UI_SPEC example.

AMBIGUITY A3 — "Career Values" Question Format

PRD lists "Career Values" as a common question but does not specify whether it is a single select, multi-select, or text input. No options are provided.

Recommendation: Implement as a single-select or multi-select card with predefined values (e.g., Helping Others, Technology, Creativity, Leadership, Stability, Entrepreneurship). This keeps the interface consistent with the card-based assessment style.

AMBIGUITY A4 — freeCodeCamp Listed in PRD but not PROMPT_SPEC

PRD (Card 7): Recommends freeCodeCamp as a learning resource.

PROMPT_SPEC (Resource Rules): Lists IBM SkillsBuild, SWAYAM, NPTEL, NCERT — freeCodeCamp is absent.

Resolution (PRD wins): Add freeCodeCamp to the backend resource mapping with its official URL. The AI does not need to mention it; the backend injects it.

MISSING M1 — No .env.example File Mentioned

BOB.md and ARCHITECTURE.md both specify required environment variables but no template file is described. Without it, setup is unclear for anyone cloning the repo.

Recommendation: Create .env.example at root and backend/.env.example with all required keys (empty values) during Phase 1.

MISSING M2 — No CORS Origin Strategy Defined

ARCHITECTURE says "configure CORS" but does not specify the allowed origin strategy for local development vs. production.

Recommendation: FRONTEND_URL env var drives the allowed origin. In development, also allow http://localhost:5173.

MISSING M3 — No watsonx.ai SDK Specified

ARCHITECTURE says "IBM watsonx.ai SDK" but does not name the Python package. The official IBM package is ibm-watsonx-ai.

Recommendation: Use ibm-watsonx-ai (PyPI) in requirements.txt. Confirm this is the correct SDK before starting Phase 5.

4 · Essential MVP Improvements

These are the only changes from the documentation that are strongly recommended. They do not add features — they prevent implementation blockers.

IMPROVEMENT 1 Client-Side PDF (resolves C1)

Use react-to-pdf or jsPDF + html2canvas on the frontend instead of a backend PDF service. This keeps the backend truly stateless, eliminates a separate backend endpoint, reduces Render resource usage, and preserves the full UI styling in the PDF automatically.

IMPROVEMENT 2 Separate context/ from hooks/ (architectural clarity)

ARCHITECTURE.md lists hooks/ but places React Context state management there implicitly. Separating context/AppContext.jsx from hooks/useAssessment.js keeps the folder clean and makes the data-flow explicit at a glance.

IMPROVEMENT 3 questions.js as a static data file (not hardcoded in components)

Centralise the full question bank (both 9–10 and 11–12 paths) in Assessment/questions.js. The question engine component simply iterates over this file. This makes the question set easy to update without touching component logic.

IMPROVEMENT 4 .env.example files (resolves M1)

Provide .env.example for both frontend and backend from Phase 1. This is a production-readiness baseline and costs nothing to implement.
